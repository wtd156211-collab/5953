# 列式整数编码库（计数器时间序列）

我们采集了一批设备的计数器，每秒一个数，一台设备一年就是三千万个点。现在用 JSONL 存，一条记录光键名就比数值长，磁盘快撑不住了。用现成的压缩也想过，问题是查某一段的时候得从头上解压下来，一次等十几秒，做不了。所以想自己写一个列式的整数编码库。

编码方案自己定，但有两条硬要求。第一，整列编码完的体积要明显小于定长存法；第二，也是最要紧的，随便给一个下标都要能**直接跳到那个位置**解出来，不许从头解一遍——这条做不到整个方案就没意义。数据不规整：有重复值，有突然跳变，偶尔来个负数，也可能一小段里全是同一个数，这些形态 samples 里都有。

另外几条：块要带校验，坏了一块要能报出是第几块，并且允许跳过它继续读后面的，不能因为中间坏一块整列就打不开；同一份数据编码两遍，输出必须逐字节一样，别掺时间戳或者随机数进去。实现只用标准库，测试用 unittest。仓库里只有这份说明和 samples/ 里的样例数据，代码从零写。

## 样例数据

samples/ 下每行一个十进制整数，`#` 开头的行是注释：

| 文件 | 点数 | 形态 | CSV 大小 |
| --- | --- | --- | --- |
| `tiny.csv` | 12 | 常量、负数、零、正负大跳变各来一点，给单测快速用 | 123 字节 |
| `ramp.csv` | 100000 | 每秒一个数，基本每次 +1，偶发 0/+2/−1 抖动 | 1.10 MB |
| `repeated.csv` | 100000 | 长时间不变，中间夹着几段几千点的完全常量 | 391 KB |
| `jumps.csv` | 50000 | 平时 ±1，每 5000 点来一次几十万量级的突然跳变 | 344 KB |
| `negatives.csv` | 50000 | 围绕 0 上下波动，含负数与零，偶尔一次 −50000 | 436 KB |
| `mixed.csv` | 150000 | 递增段、常量段、跳变、负值段混在一起 | 1.17 MB |

## 体积目标

基准是**定长存法**：每个点 8 字节（int64 小端），没有键名、没有分隔符。目标按文件算，编码后的**整列文件大小**（含块头、索引、元数据）必须不超过下表：

| 文件 | 定长基准 | 目标上限 | 相当于定长的 |
| --- | --- | --- | --- |
| `ramp.csv` | 800000 字节 | 160000 字节 | ≤ 20% |
| `repeated.csv` | 800000 字节 | 160000 字节 | ≤ 20% |
| `jumps.csv` | 400000 字节 | 80000 字节 | ≤ 20% |
| `negatives.csv` | 400000 字节 | 80000 字节 | ≤ 20% |
| `mixed.csv` | 1200000 字节 | 240000 字节 | ≤ 20% |
| 五个文件合计 | 3600000 字节 | 720000 字节 | ≤ 20% |

`tiny.csv` 只有 12 个点，单块头与索引的开销占比太高，不设比例目标。如果某个块编码后反而比定长还大，允许这一块按定长原样存（可选兜底，不强制）。

## 性能与内存目标

- **建索引**：三千万个点，常驻内存不超过 **300 MB**，且内存占用不随点数线性增长（分块流式写出，不要先把整列读进内存）；本机 SSD 上单线程建索引不超过 **5 分钟**。
- **单点随机读**：单线程、含定位与解码，每秒不低于 **20000 次**；单次读的耗时必须与下标无关，不能随下标变大而变慢。
- **坏块隔离**：单块损坏时读其它块不受影响，报错要带块号。

## 编码结果与读接口

编码结果要求能放进**一个自包含文件**（数据块 + 块索引 + 元数据），换台机器只搬这一个文件就能读。

校验算法由实现选择（CRC32 之类的都行），但每条要满足：每个块一个校验字段、随块一起存；能检出该块内的单字节翻转；校验失败时报出块号，并支持跳过该块继续读后面的块。
